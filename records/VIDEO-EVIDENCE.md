# VIDEO-EVIDENCE — the two JSON surfaces, and the one committed run summary

**Written 2026-11-08.** For a stranger: what a page can read as data, what each surface is
for, and why the run panel says what it says. Nothing here is a new measurement; it
describes surfaces the backend serves and one file generated from a recorded run.

## 1. Why these are not contract endpoints

`API_CONTRACT.md` lists nine endpoints, and `frontend/lib/api.ts` calls those nine. The
backend serves them, plus `/health`, and those ten are the rows of `ROUTES` in
`ticketpath/server.py`; `/health.contract.routesImplemented` is 10 and
`endpointsImplemented` is 9 because that is what the contract has.

The console at `/` has always been served beside the route table, not inside it, so it
cannot inflate that count. The two surfaces below are served the same way, for the same
reason extended to them: they are projections of the console, they are not in the
contract, and counting them would make the health block claim an eleven-route contract the
frontend does not call. They answer `GET` and `HEAD`; any other verb gets the console's own
rendered 405, because the route exists and the method does not.

## 2. `GET /devnet-record.json`

**What it is for.** A panel that has to show the recorded devnet transaction as data,
without scraping the console page. It is built by `Orchestrator.devnet_record`, which calls
the same `chain_client.load_artefact` the console's `[DEVNET]` slot calls, on the same
path, so the page and this document cannot be reading two different files.

The body is:

- `source`: the path the server actually read. For the operator's record that is
  `records/devnet-artefacts.json`.
- `loaded`: true when the file was read and verified, false otherwise.
- `record`: the loader's own dictionary when `loaded` is true, and `null` when it is not.
  It is not reshaped here.
- `note`: one sentence saying the server asked no cluster. The record is what the file says
  a verified run wrote, not a live read.
- `reason`: only when `loaded` is false. It names what is missing (no file at that path, or
  the loader's own reason the file did not verify) and the record stays `null`.

**What it carries for the film.** `records/devnet-artefacts.json` is the frozen record: face
1,000,000,000 lamports, cap 2,500 bps, the accepted leg at 1,250,000,000 lamports with no
error, and the refused leg at 1,250,000,001 with `custom program error: 0x177a` (`6010`,
`E_CAP_EXCEEDED`). Those are the numbers a screen may print as the chain's. The JSON also
carries every other field the loader read, unchanged.

**What it does not claim.** It is not a cluster read. `rpc_adapter` opens no socket, and the
note says so in the body. A file that does not verify is not partly shown: `loaded` is
false and `record` is null.

## 3. `GET /guidance.json`

**What it is for.** The console payload's refusals, as plain sentences, with their count,
for a page that has to print them as rows rather than as HTML. `event`, `tier` and `asOf`
name the state the sentences belong to, and `canonicalUrl` is the console URL that
reproduces it.

The refusal sentences are produced by `ticketpath.console.blocks.refusal_lines`, the same
function the console's refusal block wraps in its own `<li>` markup. The JSON prints the
plain form of that sentence: no tags, no `[REFUSED]` row badge, no code prefix. The HTML is
unchanged and is pinned by a test, so the two surfaces cannot drift.

**The default state, measured after the fixture moved to GB.** With no query parameters the
console prices its own default event, `evt_syn_02` (`synthetic-stage-cap-binding`, recorded
cap 1,500 bps), and `/guidance.json` prints **6 refusals**:

`not_identified`, `no_demand_response`, `no_fee_model`, `cap_mass_dominates`,
`no_upper_bound`, `insufficient_events`.

So on that state the voice's "an upper bound, a sale probability and four more" is true:
`no_upper_bound` is the upper bound and `not_identified` is the sale probability. The count
is a property of the selected event and of the query parameters, not a constant: the same
build prints 5 for `evt_syn_01`, and `no_upper_bound` is not among them. A take must be
checked against the count the server prints for the state being filmed.

**What it does not claim.** It is not a contract route and not a model. It repeats the
console's own refusals for one state, and a bad parameter is the same 400 the console
renders, in the error shape every JSON route uses.

## 4. The committed run summary: `frontend/data/sim-run.json`

Generated by `tools/swarm_panel.py` from one recorded run's own meta files, then checked
with `--check`. The run is `sw20261108T054830Z6297`.

| field | value |
|---|---|
| label | `SCRIPTED AGENTS · DRY RUN · SYNTHETIC` |
| run id | `sw20261108T054830Z6297` |
| recorded on | `2026-11-08`, from the run id |
| agents | 9, counted from the meta: 2 buyer, 1 holder, 2 flipper, 1 scalper, 1 sniper, 1 panic, 1 greater_fool |
| capped mode | 12 rounds, 32 tickets, 32 executed / 4 refused / 15 skipped, 51 decisions, cap 2,500 bps, ceiling 1,250,000,000 lamports |
| monitored mode | 12 rounds, 32 tickets, 64 executed / 4 refused / 38 skipped, 106 decisions, cap 65,535 bps, ceiling 7,553,500,000 lamports |
| cost | `null`, reason: scripted agents, no model calls, so no dollars were spent |
| charts | `frontend/public/charts/price-path-evt_capped.svg` and `price-path-evt_monitored.svg`, byte copies of `docs/charts/` |

**Why the label says SCRIPTED and DRY RUN.** The meta files record `llm: null` (no model
was called, so there is no token cost to print), `dry_run: true` and `cluster: local`. A dry
run simulates the chain inside the run; it does not touch a validator. The label and the
`chain` string therefore say scripted and simulated, and no frame may pair these numbers
with "local validator" or with a dollar figure. The two charts are the same run's: each
SVG's own title names `sw20261108T054830Z6297`.

**Why the meta files are not committed.** They live in `.swarm-runs/`, which is git-ignored
and names this machine's scratch layout. The tool copies only the aggregates above and the
two chart bytes. `sourceNote` in the JSON says exactly that.

## 5. How to check it

```bash
python3 tools/swarm_panel.py --check
python3 -m unittest tests.test_evidence_surfaces tests.test_swarm_panel
```

`--check` compares the committed JSON with a fresh transcription when the run's meta files
are on the machine, and always compares the two chart copies byte for byte with
`docs/charts/`. A clone has no `.swarm-runs/`; there the tool says the run comparison could
not be made, and still checks the chart bytes and the file's own claims.

## 6. What none of this is

Not evidence about a real ticket market. The fixture store is synthetic and says so on
every payload. The swarm run is a simulation by scripted agents. The devnet record is a
file this server read, not a cluster it asked. The refusals are the engine declining to
state what the record cannot support. A reader who wants the law behind the cap can follow
the citations in `ticketpath/data/region-caps.json`; a reader who wants the fixture's own
description can read `records/FIXTURE-STORE.md`.
